# EKLT Usage Guide

## Overview

EKLT still consumes the same ROS1 inputs as before:

| Topic | Message type | Default topic | Purpose |
|:-----:|:------------:|:-------------:|:-------:|
| `events` | `dvs_msgs/EventArray` | `/dvs/events` | Asynchronous events used for tracking between frames |
| `images` | `sensor_msgs/Image` | `/dvs/image_raw` | Grayscale frames used for corner extraction and KLT bootstrapping |

The repo now also contains a stage-2 bridge path for replaying a frame sequence through ROS2 and relaying it back into the existing ROS1 EKLT node.

The practical flows are:

1. Existing ROS1 direct path: bag, live camera, or any ROS1 publisher already producing `/dvs/events` and `/dvs/image_raw`.
2. Stage-2 bridge path: frame sequence or external rendering -> v2e source adapter -> ROS2 sequence source -> `ros1_bridge` -> ROS1 relay -> EKLT.
3. Default rosbag bridge demo: ROS1 rosbag + EKLT, with `ros1_bridge` exposing the same topics to ROS2 tools.

## Stage-2 Bridge Topics

The stage-2 bridge intentionally uses standard ROS message types across the ROS1/ROS2 boundary so the relay stays lightweight and does not require extra message packages.

ROS2 source topics:

| Topic | Message type | Description |
|:-----:|:------------:|:-----------:|
| `/eklt/events` | `std_msgs/UInt8MultiArray` | Encoded generic event-batch bytes generated by a pluggable source adapter |
| `/eklt/image_raw` | `sensor_msgs/Image` | Replay frame stream in `mono8` |
| `/eklt/rendered_frame` | `sensor_msgs/Image` | Copy of the rendered or replayed frame for ROS2-side visualization |
| `/eklt/event_preview` | `sensor_msgs/Image` | Event accumulation preview in `mono8` |

ROS1 relay output topics:

| Topic | Message type | Description |
|:-----:|:------------:|:-----------:|
| `/dvs/events` | `dvs_msgs/EventArray` | EKLT-compatible event stream |
| `/dvs/image_raw` | `sensor_msgs/Image` | EKLT-compatible frame stream |

EKLT output topics:

| Topic | Message type | Description |
|:-----:|:------------:|:-----------:|
| `/feature_tracks` | `sensor_msgs/Image` | Annotated feature-track visualization |

## What The Stage-2 Bridge Accepts

The stage-2 bridge reads an image sequence from disk. Each frame may be grayscale or RGB; the loader converts it to `mono8` before replay.

Event generation is not implemented locally in this repo. The default source adapter uses `v2ecore.emulator.EventEmulator` from the active Python environment. Keep `v2e` installed in the same environment used to run `eklt-sequence-source`.

Supported timing inputs:

- constant-rate playback through `sequence.fps`
- explicit per-frame timestamps through `sequence.timestamps_path`

That makes two practical entry modes:

1. Use any existing frame sequence you already have.
2. Render a sequence externally, then replay it through the bridge.

## From A Frame Sequence To Tracks

### 1. Install the Python package

From the repo root:

```bash
python3 -m pip install -e python
```

This installs the three stage-2 entrypoints:

- `eklt-sequence-source`
- `eklt-ros1-relay`
- `eklt-run-rosbag-bridge-demo`

### 2. Create a bridge config

Start from
[stage2_sequence_bridge.json](examples/stage2_sequence_bridge.json) and point
`sequence.frames_dir` to your rendered frames.

Minimal example:

```json
{
  "source": {
    "kind": "v2e_sequence"
  },
  "sequence": {
    "frames_dir": "/absolute/path/to/frames",
    "glob": "frame_*.png",
    "fps": 20.0
  },
  "v2e": {
    "pos_thres": 0.2,
    "neg_thres": 0.2,
    "device": "cpu"
  }
}
```

If you have explicit timestamps, add:

```json
{
  "sequence": {
    "frames_dir": "/absolute/path/to/frames",
    "glob": "frame_*.png",
    "timestamps_path": "/absolute/path/to/timestamps.txt"
  }
}
```

The timestamps file should contain one timestamp per line in seconds.

Use `"source": {"kind": "frames_only"}` only when you want to publish frames without event batches.

### 3. Start EKLT

ROS1 terminal:

```bash
source /opt/ros/noetic/setup.bash
roscore
```

Second ROS1 terminal:

```bash
source "$HOME/eklt_catkin_ws/devel/setup.bash"
roslaunch eklt_rebuild eklt.launch tracks_file_txt:=/tmp/eklt_tracks.txt v:=1
```

### 4. Start the bridge

ROS1 + ROS2 bridge terminal:

```bash
source "$HOME/eklt_catkin_ws/devel/setup.bash"
source /opt/ros/jazzy/setup.bash
ros2 run ros1_bridge dynamic_bridge --bridge-all-topics
```

ROS1 relay terminal:

```bash
source "$HOME/eklt_catkin_ws/devel/setup.bash"
eklt-ros1-relay --config doc/examples/stage2_sequence_bridge.json
```

ROS2 source terminal:

```bash
source /opt/ros/jazzy/setup.bash
eklt-sequence-source --config doc/examples/stage2_sequence_bridge.json
```

### 5. Inspect the outputs

ROS2-side previews:

- `/eklt/rendered_frame`
- `/eklt/event_preview`

EKLT visualization:

- `/feature_tracks`

Track file:

- `/tmp/eklt_tracks.txt` in the example command above

The track file format is:

| Column | Meaning |
|:------:|:-------:|
| feature id | integer track identifier |
| timestamp | ROS time in seconds |
| x | subpixel x position |
| y | subpixel y position |

## From External Rendering To Tracks

The supported path in this repo is:

1. render a frame sequence externally
2. replay that sequence through the stage-2 bridge
3. inspect `/feature_tracks` and `tracks_file_txt`

### External-rendering contract

The bridge expects:

- a deterministic frame sequence on disk
- file names that sort in playback order
- either `sequence.fps` or `sequence.timestamps_path`

Once those frames exist, the rest of the workflow is identical to the sequence-based path above.

## Default Rosbag Example Through The Bridge

The repo contains the original example bag at `data/eklt_example/boxes_6dof.bag`.

Run EKLT, play the bag, and expose ROS1 topics through `ros1_bridge`:

```bash
source /path/to/eklt/catkin_ws/devel/setup.bash
python3 -m pip install -e python
eklt-run-rosbag-bridge-demo \
  --bag data/eklt_example/boxes_6dof.bag \
  --tracks-file /tmp/eklt_example/tracks.txt \
  --ros1-setup "$HOME/eklt_catkin_ws/devel/setup.bash" \
  --ros2-setup /opt/ros/jazzy/setup.bash \
  --mode frame-backed
```

The runner starts:

- `roscore`
- `ros2 run ros1_bridge dynamic_bridge --bridge-all-topics`
- `roslaunch eklt_rebuild eklt.launch`
- `rosbag play data/eklt_example/boxes_6dof.bag`

Use dry-run mode to inspect exact commands:

```bash
eklt-run-rosbag-bridge-demo --dry-run
```

Use `--mode event-only` to launch the alternative FIBAR-backed initialization
path with `event_only_mode:=true` and `bootstrap:=events`.

## Visualization And Track Storage

### Visualization

EKLT’s viewer publishes the annotated tracking image on `/feature_tracks`.

That image overlays:

- the current frame
- tracked features
- flow arrows
- optional feature IDs and patch outlines

Useful display flags:

- `display_features`
- `display_feature_id`
- `display_feature_patches`
- `arrow_length`
- `scale`

### Track storage

When `tracks_file_txt` is set in `roslaunch eklt_rebuild eklt.launch`, EKLT writes one row per feature update:

```text
feature_id timestamp x y
```

This is the main artifact to archive after a run.

## Existing ROS1 Direct Usage

Nothing in EKLT itself is rosbag-specific. The original ROS1 path still works exactly as before.

### Rosbag replay

```bash
roslaunch eklt_rebuild eklt.launch tracks_file_txt:=/tmp/tracks.txt v:=1
rosbag play /path/to/recording.bag
```

### Live DAVIS driver

```bash
roslaunch dvs_ros_driver davis_ros_driver.launch
roslaunch eklt_rebuild eklt.launch tracks_file_txt:=/tmp/tracks.txt v:=1
```

### Custom ROS1 publisher

Any ROS1 publisher is acceptable if it provides:

1. `dvs_msgs/EventArray` on the `events` input
2. `sensor_msgs/Image` in `mono8` on the `images` input

The tracker always uses the most recent frame before the current event time, so events and images should arrive in chronological order.

## Configuration Notes

EKLT runtime flags still come from `config/eklt.conf` and the launch file.

Inspect them with:

```bash
rosrun eklt_rebuild eklt_node --help
```

Most important EKLT parameters:

- `min_corners`
- `max_corners`
- `batch_size`
- `patch_size`
- `tracking_quality`
- `bootstrap`
- `displacement_px`
- `first_image_t`
